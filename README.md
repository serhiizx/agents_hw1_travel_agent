# ReAct-агент «Помічник мандрівника»

## 1. Опис проєкту

ReAct-агент на LangGraph, який допомагає спланувати поїздку: підказує погоду в
місті, рахує бюджет за офіційним курсом НБУ і дає коротку довідку про місто з
Вікіпедії. Агент побудований як `StateGraph` з циклом `LLM → tools → LLM`,
працює з будь-яким OpenAI-сумісним провайдером (LM Studio, Ollama, OpenAI, проксі курсу).
Має три запобіжники (`max_steps`, `timeout`, детекція зациклення) і пише повну
траєкторію виконання у JSON. Фінальна відповідь повертається як Pydantic-модель
`FinalAnswer(answer, confidence, sources)`, зібрана програмно після графа.

## 2. Доменна задача

- **Домен:** подорожі.
- **Що вирішує агент:** відповідає на запити типу «яка погода у Львові на 3 дні»,
  «скільки гривень у 300 доларах», «чим цікава Одеса» — і на комбіновані запити,
  де треба зібрати все це разом.
- **Інструменти (tools):**
  - `get_weather` — прогноз погоди на 1–7 днів (Open-Meteo: геокодинг + прогноз);
  - `get_nbu_rate` — офіційний курс валюти до гривні (API Національного банку України);
  - `get_wiki_summary` — коротка довідка з Вікіпедії (uk/en).

Усі три API безкоштовні й не потребують ключів.

## 3. Архітектура

```
START → agent ──(є tool_calls?)──→ tools → agent
              └──(немає)─────────────────────→ END
```

- **LLM-провайдер:** `ChatOpenAI` з `base_url` із `.env`. Прогін нижче зроблено
  на локальній моделі `google/gemma-4-e4b` через LM Studio (`http://127.0.0.1:1234/v1`).
- **`agent`** — LLM з `bind_tools(TOOLS)` вирішує: викликати інструмент чи вже
  відповідати. Перед викликом моделі перевіряються всі три запобіжники.
- **`tools`** — вбудований `ToolNode(TOOLS)`, без жодних обгорток.
- **Structured output** робиться після завершення графа, у `build_final_answer()`:
  остання репліка агента загортається у Pydantic-модель
  `FinalAnswer(answer, confidence, sources)` **програмно, без другого виклику LLM**.
  `confidence` — евристика за фактами прогону: `0.9` усі викликані інструменти
  відпрацювали чисто, `0.5` хоча б один повернув помилку, `0.3` інструменти не
  викликались зовсім (відповідь із власних знань моделі), `0.0` спрацював
  запобіжник. Спершу тут був `llm.with_structured_output(...)`; від нього
  відмовились — деталі в §6.
- **Логування** теж живе у `run_agent`: `app.stream(stream_mode="updates")` віддає
  по одному оновленню на кожен відпрацьований вузол, тому вузли графа лишаються
  чистими функціями без домішки логування.
- **Захисні механізми:** `max_steps = 10`, `timeout = 90 с`,
  `LoopDetector(max_repeats = 3)`.
- `recursion_limit` LangGraph навмисно виставлений вищим за `max_steps`, щоб
  спрацював саме наш запобіжник, а не внутрішній `GraphRecursionError`.

## 4. Інструкція запуску

```bash
cd hw1_travel_agent
cp .env.example .env          # вписати свій base_url / ключ / модель

uv run pytest test_tools.py -v        # Завдання 1: тести інструментів
uv run python test_runner.py          # Завдання 4: 5 тест-кейсів + демо запобіжників
uv run python agent.py "Яка погода у Львові на 3 дні?"   # ручний запит
```

`uv` сам створить `.venv` і встановить залежності при першому `uv run` —
окремо нічого ставити не треба. Якщо `uv` немає ([інструкція зі
встановлення](https://docs.astral.sh/uv/getting-started/installation/)),
працює і класичний шлях:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python test_runner.py
```

Після `test_runner.py` з'являються `trajectory.json` і `test_results.json`.

## 5. Результати тестування

**Що перевіряє кожен кейс** (поле `checks` у `test_runner.py`, потрапляє
в `test_results.json`):

- **TC-001 · simple** — один tool call: «Яка зараз погода в Києві?» → `get_weather`.
  Перевіряє базову роботу ReAct-циклу `LLM → tool → LLM`.
- **TC-002 · medium** — 2 tool calls: «Скільки гривень коштує 250 євро і яка погода
  в Одесі?» → `get_nbu_rate` + `get_weather`. Перевіряє, чи агент планує послідовність
  дій із двох РІЗНИХ інструментів.
- **TC-003 · complex** — потребує аналізу та синтезу: «Поїздка до Львова на 3 дні
  з бюджетом 300 доларів» → `get_weather` + `get_nbu_rate` + `get_wiki_summary`.
  Перевіряє, чи агент використовує результати tools для формування комплексної
  відповіді, а не переказує три Observation'и підряд.
- **TC-004 · validation** — некоректний параметр `days=30`. Перевіряє, що Pydantic
  відхиляє вхід, а агент обробляє помилку як Observation, замість того щоб впасти
  або вигадати прогноз.
- **TC-005 · safety** — той самий запит, що TC-003, але з `max_steps=1`. Перевіряє,
  що запобіжник віддає часткову відповідь із зібраними даними, а не виняток.

Прогін на `google/gemma-4-e4b` (LM Studio), дані з `test_results.json`:

| Test ID | Складність | Кроків | Tool calls                                       | Час, мс | Статус     |
|---------|------------|--------|--------------------------------------------------|---------|------------|
| TC-001  | simple     | 2      | `get_weather` ×1                                 | 4 603   | ✅ success |
| TC-002  | medium     | 2      | `get_nbu_rate`, `get_weather`                    | 10 671  | ✅ success |
| TC-003  | complex    | 2      | `get_weather`, `get_nbu_rate`, `get_wiki_summary`| 12 946  | ✅ success |
| TC-004  | validation | 1      | жодного — модель прочитала схему              | 9 323   | ✅ success |
| TC-005  | safety     | 1      | 3 виклики, обірвано на `max_steps=1`             | 4 453   | ⚠️ partial |

Демонстрація запобіжників (кінець виводу `test_runner.py`):

- **timeout** (`timeout_s=0.001`) — залежно від того, чи встиг перший вхід у
  вузол `agent` випередити дедлайн, агент або зупиняється одразу, або віддає
  часткову відповідь із даними першого раунду інструментів;
- **max_steps** (`max_steps=1`) — те саме, але за лічильником кроків;
- **валідація** — `WeatherInput(city="Київ", days=30)` кидає
  `ValidationError: Кількість днів прогнозу має бути від 1 до 7`;
- **LoopDetector** — на третьому однаковому виклику `check()` повертає `True`.

## 6. Аналіз результатів

**Чи правильно агент обирав tools?**
Так, в усіх п'яти кейсах вибір був коректний. Найцікавіший — TC-004, і він
поводиться недетерміновано. У збереженому прогоні модель прочитала
`Field(description=...)`, побачила обмеження 1–7 днів і **взагалі не викликала**
інструмент (`tool_calls` порожній, `confidence` = 0.3). На інших прогонях того
самого запиту вона таки викликала `get_weather(city="Київ", days=30)`,
`ToolNode` перехоплював `ValidationError` і повертав його як Observation
(`Error invoking tool 'get_weather' … days: Value error, Кількість днів
прогнозу має бути від 1 до 7`), після чого агент пояснював обмеження вже з
посиланням на помилку. Обидва шляхи прийнятні: у першому опис схеми спрацював
як превентивна валідація, у другому — сама Pydantic-валідація.

На простому запиті модель
викликала рівно один інструмент, на складному (TC-003) — одразу всі три
паралельно в одному кроці. Це помітна особливість: модель не робить три
послідовні раунди `LLM → tool → LLM`, а планує всі виклики наперед і віддає
їх одним `tool_calls`-масивом. Тому «кроків» у складному кейсі стільки ж, скільки
у простому (2), хоча tool calls утричі більше.

**Де агент помилявся і чому?**
У цьому прогоні жоден із п'яти кейсів не дав хибної відповіді по суті.
Галюцинацій параметрів (порожнє місто, від'ємна сума) не було — описи у
`Field(description=...)` виявились достатньо однозначними.

На попередньому прогоні (інша модель, `gemma4` через Ollama) був показовий
збій у TC-002: агент отримав коректний Observation від `get_weather` для Одеси,
але у фінальній відповіді написав «прогноз погоди в Одесі не вдалося отримати
через технічну помилку». Інструмент відпрацював — помилилася LLM, загубивши
один із двох Observation'ів. На `google/gemma-4-e4b` це не відтворилось: у
TC-002 обидва Observation'и потрапили у відповідь.

Окремо — помилка, яку **вже виправлено**. Раніше `FinalAnswer` збирався другим
викликом LLM через `with_structured_output`. Цей крок поводився погано у три
способи. По-перше, на повторному прогоні TC-004 модель відповіла на службовий
промт замість того, щоб переформатувати відповідь агента: у полі `answer`
опинилось «Будь ласка, надайте підсумок роботи агента…». По-друге, `confidence`
на всіх без винятку кейсах дорівнював рівно `1.0` — самооцінка моделі не несла
жодної інформації. По-третє, цей виклик з'їдав приблизно половину часу запиту.
Тепер `FinalAnswer` збирається програмно у `build_final_answer()`, `confidence`
рахується з фактів прогону (див. §3), а час виконання впав приблизно вдвічі.


**Кроки: simple vs complex.**
Лінійної залежності немає: TC-001 (simple) і TC-003 (complex) обидва
відпрацювали за 2 кроки. Складність вилилась не в кількість ітерацій циклу, а
в кількість інструментів у межах одного кроку. Тобто `max_steps` для цієї
моделі — слабкий проксі складності; краще додатково лімітувати кількість
tool calls.

**Чи досягав агент max_steps або timeout?**
У штатних кейсах — ні, і не близько: при ліміті 10 реально використовувалось 2
кроки, тобто запас 5×. Спрацювання довелось форсувати штучно: TC-005 із
`max_steps=1` та демо з `timeout_s=0.001`. Обидва запобіжники відпрацювали
коректно — агент повернув часткову відповідь із поміткою причини зупинки, а не
впав із винятком.

**Залежність часу виконання від складності.**
Час зростає майже виключно за рахунок довжини відповіді LLM, а не мережевих
викликів: 4,6 с (simple) → 11–13 с (medium/complex). HTTP-запити до Open-Meteo,
НБУ й Вікіпедії займають десятки мілісекунд і в загальному часі не помітні.
Практично весь бюджет часу — це інференс локальної моделі.

**Випадки, коли агент НЕ використав tool, хоч мав би.**
На першій версії TC-004 («прогноз на 30 днів») модель відповіла з власних знань,
що прогноз обмежений 7 днями, взагалі не викликавши інструмент. Формально
відповідь правильна, але механізм валідації вона не показала — тому запит було
переформульовано на явний («виклич інструмент з параметром days=30»), і тоді
`ValidationError` дійшла до агента як Observation.

## 7. Висновки та обмеження

- **Що працює добре:** вибір інструментів, паралельні виклики, структурована
  фінальна відповідь, усі три запобіжники, повне логування траєкторії.
- **Що можна покращити:** лімітувати не лише кроки, а й сумарну кількість tool
  calls; додати ретрай на мережеві помилки інструментів.
- **Відомі обмеження:** якість помітно залежить від моделі — на `llama3` агент
  взагалі не працює (`does not support tools`); `get_weather` залежить від
  геокодера Open-Meteo, який не знаходить дрібні населені пункти; курс НБУ
  оновлюється раз на добу, тобто це не біржовий курс.

## 8. Структура файлів

- `tools.py` — Pydantic-схеми та три інструменти (Завдання 1)
- `agent.py` — LangGraph-граф, ReAct-цикл, structured output (Завдання 2)
- `safety.py` — `MAX_STEPS`, `TIMEOUT_SECONDS`, `LoopDetector` (Завдання 3)
- `logger.py` — `TrajectoryLogger` (Завдання 3)
- `test_tools.py` — unit-тести інструментів і валідації (Завдання 1)
- `test_runner.py` — тест-кейси та демо запобіжників (Завдання 4)
- `trajectory.json` — лог траєкторії TC-003 (генерується)
- `test_results.json` — результати тестів (генерується)
- `pyproject.toml` — залежності для `uv` (джерело правди)
- `uv.lock` — зафіксовані версії, щоб прогін відтворювався
- `requirements.txt` — ті самі залежності для `pip`
- `.env.example` — шаблон конфігурації LLM-провайдера
